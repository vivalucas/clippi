## 事实与文档分工

- 代码表示当前实现，已确认需求表示预期；发现冲突时先判断是 bug 还是文档过期。
- 版本以 Cargo、Xcode、csproj/manifest、安装器和 tag 为依据；C ABI 以 `core/src/types.rs` / `ffi.rs` 为依据；文档补充跨文件语义，不手抄所有字段。
- 根 README 面向使用者；AGENTS 维护协作边界；本文件维护导航与流程；CLAUDE.md 只导入 AGENTS。
- 当前约定直接更新，过期内容删除；重要原因进 11。不要恢复旧 `project-log` 的“只增不删”和每轮流水账模式。

## 开发与协作

先检查分支、工作区和相关代码，明确“需求—现有实现—本轮改动—验证方式”。小修复简述即可；跨模块、FFI 契约、任务生命周期或长期行为变化先写精简计划。已确认范围直接实施，改变产品含义或破坏兼容的选择先讨论。

多人或多任务并行时，在 01 分行登记范围、负责人和依赖；文档登记不是文件锁，不覆盖他人未提交修改。

## Git 与跨设备同步

### 项目策略

- 沿用当前分支；未经用户指令不新建/切换分支或工作树。
- 提交、推送默认由用户指令触发；版本、tag、Release 与生产发行需要分别授权。
- `main` push 会触发两端 CI artifact；`v*` tag 会创建/更新公开 Release 资产。因为 push/tag 有外部构建效果，操作前必须核对授权范围。

### 开工检查

1. 查看 `git status --short --branch`、当前分支和 upstream；文档整理不自动合并远端代码。
2. 需要开发同步时可以 fetch；只有工作区干净、upstream 明确且当前分支单纯落后时才可快进。
3. 有修改不自动 stash/reset/清理；分叉时先分析双方提交，不自动 rebase、merge 或强推。
4. Git 看不到其他设备尚未推送的工作；跨设备前要完成明确的收工同步。

### 提交与推送

只暂存归属清楚的文件或片段，提交说明描述一个目的。推送前重新 fetch 并核对 remote/upstream；未经授权不强推、不重写已共享历史、不删除分支。推送后核对远端目标提交。

普通提交推送不修改版本、不打 tag、不创建 Release。发布时按 [08](08-deployment.md) 核对版本、测试、tag、Actions 和资产。

## 日常收尾

1. 按本轮全部要求检查累计 diff 和关联路径。
2. 运行与风险相称的测试；UI 能运行时看实际窗口，静态检查不能冒充视觉验收。
3. 跨平台结果分别报告，不能把 macOS 或 CI 的通过结论写成 Windows 实机通过。
4. 更新有变化的当前状态、功能/接口约定和长期决策；普通修改不写开发日志。
5. 最终说明完成内容、验证、限制、分支和实际提交/推送状态。

## 专项评审（默认只读）

先声明代码基线和范围，阅读相关实现、测试与约定，逐条复核发现。输出项目理解、确认问题、待验证问题和体验建议；每项包含触发条件、位置、影响、证据和建议。确认问题与风险分开，体验建议不能冒充 bug。

默认不改代码或文档；用户要求修复后再进入开发流程。同一 AI 自查不称独立评审，也不通过无限多轮检查声称“没有任何 bug”。保存报告时，简短结论写 10；只有仍有交接价值的复杂评审才建 14+。

## 上下文维护

1. 当前约定只保留有效内容；09 明确区分提议、实施、完成和放弃。
2. 完成计划提取长期决策，已解决问题保留测试或防复发规则，删除无价值过程。
3. 保留未解决问题、活跃交接、用户约束和必要复现信息；不确定内容注明核对依据。
4. 调整路径同步修复引用并运行文档检查。文档整理只改文档，不顺手修改业务实现。
5. 未提交、未推送且不可恢复的工作不能当旧历史删除；已进入 Git 的完整过程不另建永久流水账。

## 信息保护

真实密钥、Cookie、签名材料、登录会话和生产数据样本不得进入文档。共享配置只记录变量名、用途和假值。运行数据库不适用；依赖目录、构建产物、下载的 ffmpeg 和本地偏好不通过 Git 跨设备同步。
